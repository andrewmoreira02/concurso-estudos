1.1 · Busca linear, busca binária e Big-O

Núcleo sugerido: 55 minutos no primeiro módulo, 40 no segundo e 25 de recuperação e questões. Ajuste ao tempo disponível. Se já conhece um tópico, tente explicá-lo de memória antes de ler; concentre-se nas lacunas.

Complexidade temporal descreve como o custo de um algoritmo cresce com o tamanho n da entrada. Busca linear examina itens em sequência: no pior caso precisa de n comparações, representado por O(n). Busca binária reduz pela metade uma lista ordenada a cada passo, produzindo O(log n).

Big-O é limite assintótico de crescimento, não tempo exato em segundos. Para entradas pequenas, uma busca linear pode ser mais simples e até mais rápida pela constante envolvida. A ordenação prévia é requisito importante da busca binária.

Exemplo resolvido · 1.1

Situação: Aplicação prática do conceito acima.

  1. Lista ordenada: [3, 7, 11, 15, 19, 24, 28, 31]. Queremos encontrar 24.
  2. Verifique o meio aproximado (índice 3, valor 15). Como 24 é maior, descarte a metade esquerda.
  3. No intervalo [19, 24, 28, 31], examine 24 (conforme escolha do meio).
  4. Foram necessárias poucas comparações, em vez de percorrer todos os oito elementos.

Conclusão: A sequência aplica o conceito às condições do exemplo.

Para lembrar: Busca binária = dados ordenados + divisão sucessiva ao meio.
Armadilha de prova: Aplicar busca binária diretamente a uma coleção não ordenada não garante resultado correto.

1.2 · Listas, pilhas, filas, conjuntos e mapas

Uma lista mantém sequência e permite elementos repetidos; uma pilha segue LIFO (último a entrar, primeiro a sair); uma fila segue FIFO (primeiro a entrar, primeiro a sair). Um conjunto evita duplicidades segundo a regra de igualdade; um mapa/dicionário associa chaves a valores.

Tabelas hash oferecem busca média próxima de O(1) em condições adequadas, mas colisões e implementação alteram o custo; uma árvore balanceada costuma permitir operações O(log n). Essas garantias não são idênticas para todas as linguagens.

Exemplo resolvido · 1.2

Situação: Aplicação prática do conceito acima.

  1. Chamados recebidos na ordem A, B, C: uma fila FIFO atende A primeiro.
  2. Histórico de desfazer uma edição: uma pilha LIFO reverte primeiro a alteração C, mais recente.
  3. Conjunto de IDs visitados evita processar o mesmo chamado duas vezes.
  4. Mapa {42: "aberta", 57: "fechada"} localiza o estado pela chave 42 sem percorrer uma lista inteira, em média se a implementação usar hash adequado.

Conclusão: A sequência aplica o conceito às condições do exemplo.

Como ler: elementos A, B e C chegam nessa ordem. Na pilha, o topo é C, então C sai primeiro (LIFO). Na fila, A está na frente e sai primeiro (FIFO). O desenho não significa que uma fila precisa ser implementada como um vetor.

Para lembrar: LIFO = PILHA; FIFO = FILA. Conjunto = valores sem duplicação; mapa = chave → valor.
Armadilha de prova: Não confunda posição em lista com chave de mapa. Uma operação O(1) média não significa tempo constante garantido em todas as situações.

1.3 · Recursão, iteração e casos-base

Recursão ocorre quando uma função resolve o problema chamando a si mesma para uma instância menor. Precisa de um caso-base que interrompa as chamadas e um passo que se aproxime dele. Uma solução iterativa usa laços e estado explícito.

Recursão pode simplificar árvores e divisão e conquista, mas usa a pilha de chamadas do programa; entradas profundas podem provocar estouro de pilha. O número de chamadas pode crescer mais rapidamente do que o necessário em uma implementação ingênua.

Exemplo resolvido · 1.3

Situação: Aplicação prática do conceito acima.

  1. somaAte(3) retorna 3 + somaAte(2).
  2. somaAte(2) retorna 2 + somaAte(1).
  3. somaAte(1) retorna 1 + somaAte(0).
  4. somaAte(0) é 0. Resultado: 3+2+1+0 = 6.

Conclusão: Para n grande, considere uma solução iterativa ou a fórmula aritmética, observadas as condições do domínio.

Para lembrar: Recursão saudável = caso-base + problema menor + progresso garantido para o caso-base.
Armadilha de prova: Esquecer o caso-base ou não diminuir o problema pode provocar recursão infinita.

Exemplo resolvido · 1.3

Situação: Calcular fatorial de 4.

  1. f(0)=1.
  2. f(4)=4×f(3); f(3)=3×f(2); f(2)=2×f(1); f(1)=1×f(0).
  3. Na volta: 1, 1, 2, 6, 24.

Conclusão: O resultado é 24; cada chamada ocupa espaço na pilha.

Orientação a objetos

2.1 · Encapsulamento, herança e composição

Encapsulamento protege invariantes por meio de uma interface de operações, em vez de permitir alteração arbitrária de estado. Herança estabelece relação de especialização quando há um 'é um'. Composição reúne objetos que colaboram quando há um 'tem um/usa um'.

Composição costuma reduzir acoplamento a hierarquias rígidas e favorecer substituição de comportamentos. Herança não é sempre proibida: é apropriada quando o subtipo realmente respeita o contrato esperado do tipo-base.

Exemplo resolvido · 2.1

Situação: Aplicação prática do conceito acima.

  1. Uma classe Ordem contém status e só permite mudar para 'fechada' após cumprir critérios.
  2. Em vez de deixar qualquer código atribuir status, forneça método fechar() que verifica regras.
  3. Para notificar cliente, Ordem usa um serviço Notificador recebido por composição.
  4. Um NotificadorEmail ou NotificadorSMS pode substituir a implementação sem exigir herança de Ordem.

Conclusão: A sequência aplica o conceito às condições do exemplo.

Injetar um Notificador em uma classe não significa automaticamente composição UML com vínculo de ciclo de vida.

Para lembrar: Herança: 'é um'; composição: 'tem/usa um'; encapsulamento: preserva regras de estado.
Armadilha de prova: Criar herança apenas para reaproveitar código pode produzir subtipos que violam o comportamento esperado.

2.2 · Sobrecarga × sobrescrita e polimorfismo

Sobrecarga (overloading) é declarar métodos com mesmo nome e listas de parâmetros diferentes, em linguagens que oferecem esse mecanismo. A seleção normalmente considera os tipos estáticos dos argumentos em compilação. Sobrescrita (overriding) é redefinir em um subtipo um método herdado compatível, com despacho dinâmico quando o mecanismo é polimórfico.

O tipo da referência define quais operações podem ser chamadas estaticamente, enquanto o objeto real pode determinar a implementação executada. Essa distinção costuma aparecer em questões conceituais.

Exemplo resolvido · 2.2

Situação: Aplicação prática do conceito acima.

  1. O objeto real é Gato.
  2. A implementação de emitir() sobrescrita é chamada.
  3. Isso é sobrescrita com polimorfismo, não duas versões com parâmetros diferentes.

Conclusão: Em Java, por exemplo, sobrecarga seria calcular(int) e calcular(int,int).

Para lembrar: Carga = parâmetros diferentes. Escrita = implementação redefinida no subtipo.
Armadilha de prova: Mudar apenas tipo de retorno não caracteriza uma sobrecarga válida em Java; o conjunto de parâmetros deve distinguir as assinaturas.
class Animal { void falar() {} }
class Cao extends Animal {
  @Override void falar() { System.out.println("au"); }
}
Animal a = new Cao();
a.falar(); // au

Sobrecarga é resolvida pelos tipos estáticos em Java; métodos de instância sobrescritos usam despacho dinâmico.

2.3 · SOLID aplicado ao projeto de software

SOLID reúne cinco princípios: SRP uma razão para mudar; OCP aberto para extensão e fechado para alteração; LSP substituição segura de subtipos; ISP interfaces específicas; DIP depender de abstrações e não de implementações concretas.

São orientações de design, não regras mecânicas. Dividir tudo em uma classe por linha não garante SRP, e criar interfaces sem necessidade pode prejudicar legibilidade. O objetivo é reduzir acoplamento desnecessário e manter contratos coerentes.

Exemplo resolvido · 2.3

Situação: Aplicação prática do conceito acima.

  1. Um controlador calcula prioridade, envia e-mail e grava logs. Três motivos diferentes podem exigir mudança.
  2. Separe políticas de prioridade, notificação e persistência conforme fronteiras reais de responsabilidade.
  3. O controlador depende de uma interface de notificação, não diretamente de uma classe SMTP específica: DIP.
  4. Nova implementação de notificação pode entrar sem alterar o fluxo central: OCP.
  5. Se implementar um subtipo, ele deve cumprir pré e pós-condições esperadas: LSP.

Conclusão: A sequência aplica o conceito às condições do exemplo.

Para lembrar: SRP mudança; OCP extensão; LSP substituição; ISP interfaces pequenas; DIP abstrações.
Armadilha de prova: LSP não é só compatibilidade sintática; o subtipo não deve surpreender consumidores do contrato.
