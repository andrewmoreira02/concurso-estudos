Fundamentos de ameaças e defesas

3 subseções com exemplos e conferência de leitura no final.

1.1 · Modelar ameaças antes de implementar defesas

Segurança começa pelo entendimento de ativos, fronteiras de confiança e possíveis ataques. Em um sistema de ordens de serviço, ativos incluem dados de clientes, credenciais e permissões de alterar uma ordem. A fronteira crítica costuma estar entre navegador, API e banco.

Defina quais dados precisam de confidencialidade, integridade e disponibilidade, quem pode acessá-los e onde a aplicação valida essa autorização. Análise de ameaça não é apenas instalar um firewall: é desenhar o fluxo e perguntar qual operação é sensível.

Exemplo resolvido · 1.1

  1. Ativo: endereço do cliente e status da ordem.
  2. Ator legítimo: técnico designado; outros usuários não devem modificar a ordem.
  3. Ameaça: enviar PATCH /ordens/42 de outra conta.
  4. Defesa: a API obtém a identidade autenticada, verifica o vínculo com a ordem 42, registra tentativa negada e responde 403 quando o usuário não possui autorização.
  5. Teste: requisitar ID próprio e de outro usuário; ambos devem ter resultados diferentes conforme autorização.
Para lembrar: Pense no percurso dado → navegador → API → banco; cada mudança de confiança exige validação.
Armadilha de prova: CORS, esconder um botão ou alterar cores na interface não substituem autorização no servidor.

1.2 · SQL Injection e XSS: canais de ataque diferentes

SQL Injection manipula consultas quando texto externo vira sintaxe SQL. Use parâmetros preparados e permissões mínimas. XSS executa código no navegador quando HTML não confiável é inserido sem tratamento adequado. Para texto HTML, use saída codificada ou APIs seguras como textContent; evite colocar dados livres em innerHTML.

O contexto importa: texto HTML, atributos, URLs e scripts exigem defesas diferentes. CSP ajuda reduzir impacto de XSS, mas não substitui codificação contextual.

Exemplo resolvido · 1.2

// Perigoso quando nome contém HTML vindo do usuário:
resultado.innerHTML = nome;

// Seguro se queremos EXIBIR texto literal:
resultado.textContent = nome;

// SQL: mantenha instrução fixa e valores separados:
db.query("SELECT id FROM cliente WHERE nome = $1", [nome]);
  1. Se nome contiver tags HTML, textContent as mostra como texto.
  2. Na consulta SQL, $1 impede que conteúdo do nome seja executado como cláusula SQL.
  3. O fluxo de defesa é distinto: navegador (XSS) versus servidor/banco (SQLi).
Para lembrar: XSS: contexto de SAÍDA; SQLi: contexto da CONSULTA. Em ambos, preserve separação dado/código.
Armadilha de prova: Um token JWT, HTTPS e um WAF não garantem que código vulnerável esteja livre de XSS ou SQL Injection.
A leitura é uma marcação pessoal reversível. Não demonstra domínio.

1.3 · CSRF, cookies e proteção contextual

CSRF induz o navegador autenticado a enviar uma operação indesejada a um serviço que confia automaticamente em credenciais anexadas, como cookies de sessão. A proteção inclui tokens antifalsificação, verificação de origem em operações sensíveis e cookies com atributo SameSite apropriado.

Cookies HttpOnly reduzem acesso por JavaScript a seu valor; Secure limita envio a HTTPS. Uma requisição com bearer token colocado explicitamente no cabeçalho apresenta dinâmica diferente de um cookie enviado automaticamente.

Exemplo resolvido · 1.3

  1. Uma aplicação usa cookie de sessão e possui POST /alterar-email.
  2. Uma página de outro domínio tenta provocar o envio da requisição.
  3. O servidor exige um token antifalsificação específico da sessão, além da autenticação, e rejeita chamadas sem esse token.
  4. O cookie é configurado com SameSite adequado, Secure e HttpOnly, conforme o fluxo real de login.

Teste o endpoint diretamente, sem depender de o formulário estar escondido no frontend.

Para lembrar: CSRF abusa da credencial que o navegador envia automaticamente; autenticação não autoriza a intenção do usuário.
Armadilha de prova: CORS não é defesa suficiente contra CSRF; uma requisição pode ser enviada mesmo quando a resposta não pode ser lida por JavaScript.
A leitura é uma marcação pessoal reversível. Não demonstra domínio.

Identidade, autorização e tokens

3 subseções com exemplos e conferência de leitura no final.

2.1 · Autenticação e autorização por objeto (BOLA/IDOR)

Autenticação verifica quem é o usuário; autorização decide o que ele pode fazer. Em APIs, a checagem precisa ocorrer também no objeto específico solicitado: ter sessão válida não significa poder consultar qualquer cliente_id fornecido na URL.

BOLA (Broken Object Level Authorization) ocorre quando uma API não valida corretamente se um usuário pode acessar determinado objeto. Uma política RBAC ajuda a definir papéis, mas a regra fina de pertencimento ou responsabilidade continua necessária.

Exemplo resolvido · 2.1

// Exemplo ilustrativo de pseudocódigo de API:
const ordem = await buscarOrdem(req.params.id);
if (!ordem) return resposta(404);
if (!podeVer(req.usuario, ordem)) return resposta(403);
return resposta(200, ordem);
  1. O login identifica o usuário.
  2. A API carrega a ordem 42 e verifica sua vinculação e seu papel.
  3. Um usuário autorizado recebe 200; outro, sem permissão, é bloqueado.

É possível retornar 404 em cenários específicos para evitar exposição da existência de recursos; a estratégia deve ser consistente e intencional.

Para lembrar: Identidade responde QUEM. Autorização responde O QUE e SOBRE QUAL OBJETO.
Armadilha de prova: Não confunda 401 (não autenticado/credencial inadequada) com 403 (autenticado, mas sem permissão).

2.2 · OAuth 2.0, OpenID Connect e PKCE

OAuth 2.0 é um framework de autorização delegada; OpenID Connect (OIDC) acrescenta uma camada de identidade padronizada. No fluxo Authorization Code com PKCE, um cliente recebe um código de autorização e usa um code_verifier para provar posse quando troca o código por tokens.

O desafio code_challenge geralmente usa SHA-256 do verificador (método S256). Isso reduz ataques de interceptação do authorization code. Client Credentials é fluxo voltado a comunicação entre serviços e não representa login de usuário final.

Exemplo resolvido · 2.2

  1. Aplicação web inicia login com code_challenge e redireciona ao servidor de autorização.
  2. Após autenticação, recebe authorization_code pela URL de retorno.
  3. Envia o código e o code_verifier ao endpoint de token.
  4. O servidor calcula o desafio a partir do verificador e compara com o enviado inicialmente.
  5. Se conferir, entrega os tokens conforme política de segurança.
Para lembrar: OAuth delega acesso; OIDC informa identidade; PKCE protege a troca do código.
Armadilha de prova: Refresh token não é token de acesso; ID Token não deve ser usado como autorização genérica para todas as APIs.

2.3 · JWT: assinatura, expiração e validação

Um JWT típico tem três partes Base64URL: header, payload e assinatura. A assinatura permite detectar alteração e verificar o emissor quando a chave correta é usada; isso não significa criptografia do conteúdo. Um token legível não deve carregar segredos de negócio.

Uma API deve validar a assinatura, algoritmo permitido, emissor (iss), público-alvo (aud) e tempo (exp, quando presente), além de aplicar autorização no endpoint. A rotação de chaves e a revogação de sessões exigem desenho específico.

Exemplo resolvido · 2.3

  1. API A aceita tokens emitidos por https://id.exemplo e destinados a api-casan.
  2. Recebe um JWT válido em assinatura, mas com aud = outro-servico.
  3. Mesmo que a assinatura seja válida, o token deve ser rejeitado por público incorreto.
  4. Depois de validar o token, a API ainda verifica se o usuário pode consultar o cliente solicitado.
Para lembrar: Token assinado não é token secreto. Assinatura garante integridade/autenticidade da origem; não confidencialidade.
Armadilha de prova: Nunca aceite o algoritmo declarado pelo próprio token sem uma lista de algoritmos permitidos pelo servidor.

HTTP, APIs e segurança operacional

3 subseções com exemplos e conferência de leitura no final.

3.1 · REST: verbos, idempotência e códigos HTTP

REST organiza recursos por URIs e usa semântica HTTP. GET consulta, POST geralmente cria ou executa ações não idempotentes, PUT substitui a representação de um recurso e é idempotente por semântica, PATCH altera parcialmente conforme o patch definido; PATCH não é necessariamente idempotente.

Idempotência significa que repetir a operação tem o mesmo efeito pretendido que executá-la uma vez. Códigos usuais: 200 sucesso, 201 criado, 204 sem corpo, 400 solicitação inválida, 401 autenticação necessária, 403 acesso proibido, 404 ausente, 409 conflito, 429 limite e 500 erro interno.

Exemplo resolvido · 3.1

  1. GET /ordens/12 lê a ordem 12.
  2. PUT /ordens/12 com representação completa do estado desejado tende a produzir o mesmo resultado ao repetir.
  3. POST /ordens duas vezes pode criar duas ordens diferentes, se a API não implementar chave de idempotência.
  4. DELETE /ordens/12 remove; repetir a operação não deve apagar recursos adicionais, embora o código de resposta possa mudar.
Para lembrar: GET/PUT/DELETE têm semântica idempotente; POST não é idempotente por padrão.
Armadilha de prova: Código HTTP não substitui autorização; 200 não deve indicar sucesso quando a regra negou a operação.

3.2 · CORS, preflight e limites da origem

CORS é um mecanismo do navegador que controla se scripts de outra origem podem ler respostas HTTP. Algumas solicitações incluem um preflight OPTIONS, pedindo autorização antes de enviar a operação real. O servidor responde com cabeçalhos como Access-Control-Allow-Origin.

CORS não é sistema de login nem autorização do objeto; clientes fora do navegador, como scripts e ferramentas HTTP, não aplicam a mesma política de leitura. A origem confiável deve ser configurada conforme o fluxo e não com permissão universal quando credenciais estão envolvidas.

Exemplo resolvido · 3.2

  1. Site A faz fetch para API B enviando cabeçalho de autorização.
  2. O navegador pode enviar primeiro OPTIONS com origem e cabeçalhos solicitados.
  3. API B retorna os cabeçalhos CORS adequados e o navegador prossegue.
  4. Se CORS falhar, o script não consegue ler a resposta; isso não torna o endpoint invulnerável a requisições externas.
Para lembrar: CORS controla leitura por scripts de navegador; não é substituto de autenticação nem de anti-CSRF.
Armadilha de prova: Permitir origem '*' com credenciais é inadequado e o navegador restringe essa combinação.

3.3 · Segredos, logs, testes SAST/DAST/SCA e DevSecOps

Uma prática DevSecOps integra segurança ao desenvolvimento. SAST examina código-fonte, DAST testa aplicação em execução e SCA identifica riscos em bibliotecas/dependências. Nenhuma ferramenta isolada substitui revisão, modelagem de ameaças ou monitoramento.

Segredos como chaves privadas e tokens administrativos não devem ficar em Git público nem no JavaScript do navegador; use cofre/variáveis de ambiente do backend com menor privilégio. Logs precisam permitir investigação sem registrar senha, token completo ou dados sensíveis em excesso.

Exemplo resolvido · 3.3

  1. Antes do merge: executar análise estática e verificação de dependências.
  2. Em ambiente de teste: executar testes dinâmicos contra endpoints de autenticação e autorização.
  3. Antes da implantação: verificar rotação de segredos e permissões de conta de serviço.
  4. Após implantação: monitorar 401/403 anormais, erros 500 e limites, sem gravar tokens de sessão em texto.
Para lembrar: SAST = fonte, DAST = aplicação rodando, SCA = componentes externos.
Armadilha de prova: Passar num scanner não significa aplicação segura; vulnerabilidades de lógica de negócio exigem cenários e revisão humana.
