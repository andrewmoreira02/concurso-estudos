Modelagem relacional e integridade

3 subseções com exemplos e conferência de leitura no final.

1.1 · Entidades, relacionamentos e cardinalidade

O modelo entidade-relacionamento (DER) representa objetos sobre os quais precisamos guardar dados e os vínculos entre eles. Uma entidade Cliente tem atributos como cliente_id e nome; uma entidade OrdemServico tem os_id, cliente_id e status.

Cardinalidade diz quantas ocorrências podem participar de um vínculo: um cliente pode abrir várias ordens; cada ordem deve pertencer a um cliente. Essa regra 1:N é implementada colocando a chave do cliente na tabela de ordens, não duplicando todos os campos do cliente.

Exemplo resolvido · 1.1

  1. Identifique os objetos: Cliente e OrdemServico.
  2. Defina um identificador estável por entidade: cliente_id e os_id.
  3. Traduza a regra: uma ordem referencia exatamente um cliente; um cliente pode ter zero ou muitas ordens.
  4. Ao consultar o cliente 7, encontre suas ordens por WHERE cliente_id = 7.

Uma linha em Cliente e três linhas em OrdemServico referenciando o mesmo cliente_id representam um cliente com três solicitações, sem repetir seu endereço em cada ordem.

Para lembrar: Pergunte: quem é a entidade? Qual chave identifica uma linha? Em qual lado fica a chave estrangeira?
Armadilha de prova: N:N geralmente exige uma tabela associativa: em vez de repetir colunas de produto em pedido, use ItemPedido com chaves de pedido e produto.

1.2 · Chaves, NULL e integridade referencial

A chave primária identifica unicamente cada linha e não admite NULL. A chave estrangeira liga a outra tabela e impõe integridade referencial. UNIQUE impede duplicações, CHECK restringe valores e NOT NULL torna o preenchimento obrigatório.

NULL significa dado ausente ou desconhecido. Comparar coluna = NULL não identifica nulos em SQL: use IS NULL. A lógica SQL trabalha com verdadeiro, falso e desconhecido; por isso condições com NULL exigem atenção.

Exemplo resolvido · 1.2

CREATE TABLE cliente (
  id INTEGER PRIMARY KEY,
  nome VARCHAR(100) NOT NULL
);
CREATE TABLE ordem_servico (
  id INTEGER PRIMARY KEY,
  cliente_id INTEGER NOT NULL,
  situacao VARCHAR(16) NOT NULL
    CHECK (situacao IN ('aberta','fechada')),
  FOREIGN KEY (cliente_id) REFERENCES cliente(id)
);
  1. Insira o cliente 3.
  2. Uma ordem com cliente_id = 3 atende à regra de referência.
  3. Uma ordem com cliente_id = 99, sem cliente 99, é rejeitada pela FK.
  4. Para selecionar ordens ainda sem data de término, use WHERE encerrada_em IS NULL, se essa coluna existir.
Para lembrar: PK identifica; FK relaciona; UNIQUE evita repetição; CHECK limita valores; NOT NULL exige informação.
Armadilha de prova: FK não exige que a coluna seja única: várias ordens podem referenciar o mesmo cliente, e uma FK pode aceitar NULL se não houver NOT NULL.

1.3 · Normalização: da 1FN à 3FN

1ª Forma Normal: cada campo deve conter valor atômico segundo o modelo; evite listas de telefones em uma única célula. 2ª Forma Normal: estando na 1FN, atributos não-chave devem depender da chave inteira, especialmente quando a chave é composta. 3ª Forma Normal: estando na 2FN, atributos não-chave não devem depender transitivamente de outro atributo não-chave.

Normalizar diminui redundâncias e anomalias de inserção, alteração e exclusão. Não é obrigatório separar tudo em tabelas excessivas: a modelagem deve considerar as regras do negócio e consultas reais.

Exemplo resolvido · 1.3

  1. Considere PedidoItem(pedido_id, produto_id, nome_produto, quantidade, nome_cliente), com chave (pedido_id, produto_id).
  2. nome_produto depende apenas de produto_id, logo causa dependência parcial: crie tabela Produto.
  3. nome_cliente depende de cliente_id associado ao pedido, não de cada item: crie Cliente e guarde a referência em Pedido.
  4. O modelo resultante Cliente, Pedido, Produto e ItemPedido reduz atualização duplicada. Alterar o nome de um produto requer mudar uma linha em Produto.
Para lembrar: 1FN: valores atômicos; 2FN: depende da chave TODA; 3FN: não depende de outro atributo não-chave.
Armadilha de prova: Estar na 3FN não significa que toda consulta será rápida: JOIN e índices continuam necessários.

Consultas SQL e raciocínio com resultados

3 subseções com exemplos e conferência de leitura no final.

2.1 · SELECT, WHERE, GROUP BY, HAVING e ordem lógica

Uma consulta usa SELECT para projetar colunas, FROM para definir a fonte, WHERE para filtrar linhas, GROUP BY para formar grupos e HAVING para filtrar grupos agregados. ORDER BY ordena o resultado final.

A ordem lógica simplificada é FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Não confunda COUNT(*), que conta linhas, com COUNT(coluna), que não conta valores NULL daquela coluna.

Exemplo resolvido · 2.1

SELECT situacao, COUNT(*) AS total
FROM ordem_servico
WHERE cliente_id = 7
GROUP BY situacao
HAVING COUNT(*) >= 2
ORDER BY total DESC;
  1. O WHERE considera só as ordens do cliente 7.
  2. O GROUP BY separa as ordens por situação.
  3. O HAVING deixa somente situações com pelo menos duas ordens.
  4. O SELECT mostra situação e total; o ORDER BY organiza pelo total decrescente.
Para lembrar: WHERE filtra LINHAS antes da agregação; HAVING filtra GRUPOS depois da agregação.
Armadilha de prova: Coluna comum no SELECT de uma consulta agregada normalmente deve estar no GROUP BY; não presuma que COUNT de uma coluna inclui NULL.

2.2 · INNER JOIN e LEFT JOIN: diferença de linhas

INNER JOIN mantém pares de linhas que satisfazem a condição de junção; LEFT JOIN mantém todas as linhas da tabela à esquerda, preenchendo com NULL as colunas à direita quando não houver correspondência. A condição deve descrever a relação correta; omiti-la pode produzir um produto cartesiano.

Quando há várias linhas correspondentes, a junção aumenta o número de linhas. Por isso a contagem posterior deve ser feita com consciência: COUNT(o.id) conta ordens, COUNT(*) em LEFT JOIN conta inclusive a linha do cliente sem ordem.

Exemplo resolvido · 2.2

SELECT c.nome, COUNT(o.id) AS total_ordens
FROM cliente AS c
LEFT JOIN ordem_servico AS o
  ON o.cliente_id = c.id
GROUP BY c.id, c.nome
ORDER BY c.id;
  1. Ana possui duas ordens; Beto não possui nenhuma; Carla possui uma.
  2. INNER JOIN traria apenas Ana (duas linhas) e Carla (uma linha).
  3. LEFT JOIN preserva também Beto com o.id = NULL.
  4. O resultado agrupado é Ana 2, Beto 0, Carla 1: usamos COUNT(o.id).
Para lembrar: LEFT = preserva a ESQUERDA; INNER = apenas linhas com correspondência.
Armadilha de prova: Colocar WHERE o.situacao = 'aberta' após um LEFT JOIN elimina clientes sem ordem, porque NULL não satisfaz a condição; se for o caso, filtre no ON.

2.3 · EXISTS, NOT EXISTS e os perigos de NULL

EXISTS testa a existência de pelo menos uma linha correlacionada. Para procurar clientes sem pedidos, prefira NOT EXISTS quando precisa evitar dificuldades com NULL. NOT IN pode produzir resultados inesperados se a subconsulta devolver NULL.

A subconsulta correlacionada usa uma coluna da consulta externa, como c.id. O otimizador pode transformá-la internamente em uma estratégia eficiente; não há regra absoluta de que JOIN seja sempre mais rápido que subconsulta.

Exemplo resolvido · 2.3

SELECT c.id, c.nome
FROM cliente AS c
WHERE NOT EXISTS (
  SELECT 1
  FROM ordem_servico AS o
  WHERE o.cliente_id = c.id
);
  1. Para cada cliente, a condição busca qualquer ordem ligada a ele.
  2. Se encontrar uma, EXISTS seria verdadeiro e NOT EXISTS falso: exclui o cliente.
  3. Se não encontrar nenhuma, NOT EXISTS será verdadeiro: inclui o cliente.
  4. Com Ana (2), Beto (0), Carla (1), o resultado contém apenas Beto.
Para lembrar: EXISTS pergunta 'existe uma linha?'; NOT EXISTS pergunta 'não existe nenhuma?'.
Armadilha de prova: id NOT IN (1, NULL) não retorna simplesmente todos os IDs diferentes de 1; o NULL pode tornar a comparação desconhecida.

Transações, desempenho e segurança

3 subseções com exemplos e conferência de leitura no final.

3.1 · ACID, commit e rollback

Uma transação reúne várias operações em uma unidade de trabalho. Atomicidade exige tudo ou nada; Consistência respeita restrições; Isolamento trata interferência entre transações; Durabilidade mantém resultados confirmados conforme a garantia do SGBD.

COMMIT confirma; ROLLBACK desfaz alterações ainda não confirmadas. O nível de isolamento importa: leituras sujas, não repetíveis, fantasmas e conflitos de escrita são comportamentos distintos.

Exemplo resolvido · 3.1

BEGIN;
UPDATE conta SET saldo = saldo - 30 WHERE id = 1;
UPDATE conta SET saldo = saldo + 30 WHERE id = 2;
COMMIT;
  1. Conta 1 começa com 100; conta 2 com 50.
  2. Após as duas operações, os saldos tornam-se 70 e 80.
  3. A soma 150 foi preservada. Se houver falha antes do COMMIT e o sistema executar ROLLBACK, os dois saldos voltam ao estado anterior.
  4. Na aplicação real, valide saldo disponível e trate concorrência antes de confirmar.
Para lembrar: A = tudo/nada; C = regras válidas; I = interferências controladas; D = confirmada, persistida.
Armadilha de prova: ACID não significa que qualquer isolamento elimina todas as anomalias: revise qual nível foi configurado.

3.2 · Índices e planos de execução

Um índice é uma estrutura auxiliar que ajuda localizar e ordenar registros, mas ocupa espaço e impõe manutenção em INSERT/UPDATE/DELETE. Índices B-tree são comuns para igualdade, intervalos e ordenação; a decisão depende da seletividade da coluna e dos filtros usuais.

EXPLAIN mostra o plano escolhido pelo SGBD; EXPLAIN ANALYZE executa a consulta e mede tempos/linhas, então use com cuidado em sistemas de produção. Um sequential scan não é sempre problema: pode ser mais barato ler uma tabela pequena inteira.

Exemplo resolvido · 3.2

CREATE INDEX idx_ordem_cliente_data
ON ordem_servico (cliente_id, criada_em);
SELECT id, criada_em FROM ordem_servico
WHERE cliente_id = 7
ORDER BY criada_em DESC;
  1. A consulta filtra por cliente e ordena por data.
  2. Um índice começando por cliente_id pode atender ao filtro e apoiar a ordem.
  3. Compare o plano antes/depois, cardinalidade e quantidade de linhas lidas. Se a tabela tiver dez linhas, não presuma ganho significativo.
Para lembrar: Índice é ferramenta para acesso, não substituto de modelagem ou consulta correta.
Armadilha de prova: Criar índice em toda coluna aumenta escrita e tamanho; a posição das colunas em índices compostos altera usos possíveis.

3.3 · SQL Injection e consultas parametrizadas

SQL Injection ocorre quando a aplicação concatena entrada de usuário no texto de uma instrução SQL, permitindo alterar sua estrutura. A defesa principal é separar comando de dados com parâmetros preparados, além de validar o tipo e usar a menor permissão necessária no banco.

Uma parametrização trata o texto recebido como valor, inclusive aspas e operadores. Escapar manualmente strings não oferece o mesmo contrato; nomes de coluna ou tabela dinâmicos exigem lista de opções permitidas, pois placeholders normalmente aceitam valores, não identificadores SQL.

Exemplo resolvido · 3.3

// Exemplo conceitual com cliente PostgreSQL:
// Errado: monta a instrução com texto livre
const inseguro = "SELECT * FROM cliente WHERE nome = '" + nome + "'";
// Certo: texto SQL fixo, dados separados
const sql = "SELECT * FROM cliente WHERE nome = $1";
const parametros = [nome];
await db.query(sql, parametros);
  1. O usuário pode digitar qualquer nome, inclusive apóstrofo.
  2. O parâmetro $1 é enviado separadamente da sintaxe SQL.
  3. O SGBD interpreta o dado como texto, não como uma cláusula OR ou outro comando.
Para lembrar: Dado do usuário entra em PARÂMETRO, nunca em pedaço da sintaxe SQL.
Armadilha de prova: Validar só no frontend não protege a API: a requisição pode ser enviada diretamente ao servidor.

Questão autoral 1. Uma consulta deve incluir todos os clientes, inclusive os que não têm ordens. Qual estratégia atende ao requisito?

Gabarito B: LEFT JOIN preserva todos os clientes; COUNT(o.id) ignora o NULL da tabela de ordens. INNER JOIN perderia os clientes sem ordens; CROSS JOIN multiplicaria linhas; HAVING apenas filtraria grupos.

Questão autoral 2. Em uma tabela com chave composta (pedido_id, produto_id), nome_produto depende só de produto_id. Qual problema ocorre?

Gabarito C: Um atributo não-chave depende de parte de uma chave composta, violando a 2FN; não é um problema ACID ou um requisito de índice.

Questão autoral 3. Qual forma evita que entrada de usuário altere a estrutura de uma consulta SQL?

Gabarito B: Placeholders/consultas preparadas separam sintaxe de dados. Os demais mecanismos não impedem manipulação da SQL do backend.
